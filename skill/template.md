## 开发流程（relay v7）

本段由 relay 安装，要修改请改模板后重新安装，不要在项目里手改。适用于会修改代码、配置或测试的任务；纯提问和只读排查不适用。

**向用户提问**（任何对话都适用，不限改代码）：需要用户在几个选项中做决定时，工具支持弹出选择框（如 Claude Code 的 `AskUserQuestion`、Codex 的 `request_user_input`）就用选择框，推荐项放第一个；说明和结论仍用文字。不支持时用文字列选项。

**委派豁免**：如果你是被委派的执行方（任务里已给出验收命令），跳过第 2 步，按任务说明直接实现；除非任务明确要求，不提交、不推送。

1. **分档**
   - 微小：错别字、注释、≤10 行且需求无歧义、不触及本文件的安全不变量 → 直接改，完成后一句话说明改了什么、怎么验证的。
   - 高风险：触及本文件的安全不变量，或无法单独回滚 → 下面每一步都不能跳。
   - 其余为常规。拿不准时按高一档处理。
2. **对齐需求，开工前停下等用户回复。** 事实（现值、位置、调用方、现有测试）自己查，不问用户。用白话发一条消息：
   - 要做的：一句话，写用户能看到的变化。
   - 不会变的：一句话。
   - 需要你定的：最多 3 个，每个附选项和推荐答案。问题有依赖时只问最上游的；超过 3 个说明需求还没成形，先问最上游的一个或拆小任务。
   - 我默认这样做：有合理默认的取舍列在这里，用户不同意再改。
   - “需要你定的”按上方“向用户提问”的方式问。选择框没有得到回答，视为用户未回复，不得开工。
   - 用户回复（如 `1A`、`同意`）前不改任何文件。技术版验收条件留作内部材料（写委派说明和验收用），不发给用户。
3. **开工前**：`git status` 必须干净，否则先请用户决定提交或 stash。改动拆成可单独提交、单独回滚的小片，一个提交只做一件事。
4. **实现**：只做确认过的范围，范围外的问题记下来报告，不顺手改。修 bug 的回归测试必须在撤掉修复后失败。发现必须超出确认范围才能完成、或失败反复指向方案本身时，停下回到第 2 步重新对齐，不硬改。
5. **验收**，分两部分报告，不合并：
   - 测试：运行的命令和退出码，失败如实报告。
   - 需求：逐条对照确认过的需求，每条给 ✅/❌ 和 `文件:行`；没有测试覆盖的明说。另查 diff 有无范围外改动、有无删除或放宽已有测试。
   - 高风险档：提交前由未参与实现的子代理或新会话按确认过的需求审 diff，结论附在报告里；实现方已由别的代理审查（如委派场景）时不重复。
6. **交付**：按本文件同步文档；提交说明写做了什么、用户确认过的取舍（选了什么、没选什么）和回滚影响；推送、部署、重启前先问用户；任务结束时工作区干净。任务中发现以后还会用到的新约束或踩过的坑，在报告里提议写到哪里，用户点头再写：默认写进对应的模块文档；只有每次任务都必须遵守的规则才进本文件，进的同时检查能否删除或合并旧规则。一次性细节不写。
